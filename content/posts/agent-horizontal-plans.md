让 Agent 先出一份开发计划，交回来的列表经常是这四行：数据库迁移、服务层、API、前端。每一步要用的东西前一步都备好了，单看顺序挑不出毛病。

Dex Horthy 在《Why Software Factories Fail》里给这种排法起了个名字，叫“横向计划”，按技术栈从下往上一层层做。他说模型特别爱这么排，麻烦是做的过程中你摸不到东西。他开发几乎每个功能，都要时不时开浏览器看一眼，或者拿 curl 打一下接口。按横向计划，这些要等到最后一层前端写完才能做。

他举了个参照：没有 AI 的时候，很少有人连写两千行、甚至五百行代码，中途一次都不检查。

他自己以前手写代码是从中间往外长的。先定 API 契约，接口返回 mock 数据，用 curl 试；再写前端吃这份 mock，在浏览器里调。服务层、数据库迁移、业务逻辑和错误处理是后来一层层接进去的，每接一层都试一遍、改一遍。这种做法他叫竖切，vertical slices。

现在派活给模型，他大多数时候一次只让它做 1 到 3 片，边做边看代码。碰到他很在意的代码，或者信不过模型的地方，每一步都看，看 100 到 200 行就调一次方向，比做完两千多行再回头找哪坏了便宜。

他还说，大多数前沿模型没人引导就排不出竖切的计划，换个代码库、换个任务切法也不同，所以计划这一步他自己盯着。这是他的经验判断，文章里没有给数据。

我让 Claude Code 或 Codex 出计划，计划交回来后先问一句：第一步做完，我能试到什么？**答不上来，就让它重排。**

重排后的第一片只用 mock 把接口和页面接上，curl 打得通、浏览器里点得动就行；后面每片在上一片上加一点，比如把 mock 换成真的服务层。一次派 1 到 3 片，做完我先跑一遍，再放它往下走。

![先做能试的一片](/posts/images/agent-horizontal-plans/agent-horizontal-plans-01.png)

一片切多大，Dillon Mulroy 的数可以拿来对照。他是 Cloudflare 的工程师，在 Jan-Niklas Wortmann 的一期访谈里说，自己尽量把每个 PR 控制在 300 到 800 行，用 stacked PR 一层层叠，这个量审的时候眼睛不会发花。他说有了 AI 以后，自己交付的方式一点没变。他讲的是一次审多少行，没提竖切，我拿这个数当一片的上限。

没界面的任务，Dex 和 Dillon 都没说怎么切，下面是我的做法。命令行工具先把命令、参数和输出格式定下来，里面全返回假数据，在终端里敲一遍，看参数顺不顺手、输出对不对。写库就先写调用方的示例代码。

竖切要多写 mock，后面还得拆，接口一改 mock 也得跟着改。这些活我认，换来的是方向错了只丢一片。
