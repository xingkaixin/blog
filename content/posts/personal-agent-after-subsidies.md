关于 Personal Agent 创业，有一种流传很广的论断：今天的个人助理就像“2012 年的滴滴”。

推论是这样的：个人助理要消耗大量 token，初创团队自己承担不起；上游模型和云厂商为了争未来的入口，会通过投资和算力补贴把这些应用推向大众。最后跑出来的团队，既能拿到大厂补贴，又能靠硬件入口和自训小模型降本。

但这套逻辑里少了一个最根本的前提：当补贴撤掉之后，用户凭什么继续为个人助理付钱？

我说的 Personal Agent，是能长期保存个人信息、跨应用持续办事的助理。它确实比单次问答贵。但“做起来贵”和“用户愿意长期付钱”是两件事，前者不能推出后者。

滴滴这个类比有一部分成立。当年网约车的补贴背后，是腾讯和阿里的移动支付之争。不过按[清华大学的相关研究](https://www.cideg.tsinghua.edu.cn/upload_files/file/20190612/1560329154294055378.pdf)，大规模补贴主要发生在 2014 年，“2012 年的滴滴”这个时间点并不准确。

更大的区别在需求和网络效应。乘客本来就要从 A 地到 B 地，补贴只是降低了第一次用手机叫车的门槛。打车还有双边网络效应：车越多，乘客等得越短，规模本身就是壁垒。

个人助理没有这层效应。整理邮件、安排日程、跟进待办，哪些任务值得用户长期托付，还在一项项验证。一个助理多了十万个用户，也不会因此更了解你。底座能力可以共享，每个人的记忆和授权只能单独建立。

所以补贴换不来打车那样的壁垒。多出来的注册用户，只会带来更多后台账单。

这些账单确实不小。Manus 的[计费说明](https://manus.im/help/credits)把消耗分成模型 token、虚拟机和第三方 API 三部分。它是通用任务 Agent，不能代表所有个人助理，但能看出多步骤执行的成本结构：用户只发了一句话，后台可能已经调用了几十次工具、解析网页、执行代码。

长期助理还要决定何时调取记忆、何时更新档案、何时主动提醒。把资料存下来，和每次都把它完整塞进上下文，成本差得很远。

Manus 在 2025 年的[技术文章](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)里，把提高缓存命中率作为控制成本的核心手段，并把资料留在文件里按需读取。团队当时选择先围绕现成的商业模型做上下文工程，换取更短的迭代周期。

![个人资料保留在档案中，只读取当前任务需要的日程信息](/posts/images/personal-agent-after-subsidies/personal-agent-after-subsidies-01.png)

成本很大程度上取决于产品承诺做什么，以及怎么实现。只做一项垂直流程，和全天候跟踪用户生活里的所有变化，计算量不在一个量级。“赛道贵”推不出“初创公司没机会”。

上游愿意出钱也是事实。[Google Cloud 创业计划](https://cloud.google.com/startup/early-stage)给符合条件的 AI 初创企业最高 35 万美元的云额度，分两年发放。但项目 FAQ 写明，第三方模型不在额度覆盖范围内。

对一个主要调用其他厂商模型的个人助理，最大的一块 token 开销，这笔额度并不承担。补贴给了，用法也被限定了。

这正是上游和应用方利益不一致的地方。云厂商希望应用留在自己的生态里；应用方需要按能力和价格随时切换模型供应商。额度用完以后，真实的运行成本要由团队自己付。

**团队需要算清楚的是：没有补贴时，可靠完成一件用户愿意付钱的事，到底要花多少钱。**

这笔账除了 token 和服务器，还包括失败后的重试和返工。更容易漏掉的是用户检查和接管的时间。换成便宜的小模型以后，如果出错率明显上升，用户为了避免邮件发错、日程撞车，就得每次从头核对一遍。省下的调用费，抵不过用户多花的这些时间。

![用户修正日程冲突，接管时间也属于个人助理的使用成本](/posts/images/personal-agent-after-subsidies/personal-agent-after-subsidies-02.png)

用户为个人助理付费，是为了做完之后可以不用再看。能稳定做到这一点，才有定价权。模型单价便宜，不自动变成竞争优势。

自训小模型也要放在这笔账里算，它更适合后期降本：流程足够收敛，攒够了高质量的执行轨迹，也能稳定验证交付质量，自训才可能比调用商用 API 便宜。在这之前，Prompt Cache、减少中间步骤、把非核心环节交给便宜模型，门槛都低得多。

硬件确实能拿到软件拿不到的上下文。Plaud 这类录音设备在谈话发生时就开始记录，省掉事后上传整理，其[会员方案](https://www.plaud.ai/pages/plaud-ai-plan-pricing)按转写时长分档收费。但录到声音不等于理解用户，用户也未必会一直戴着它，并交出邮箱和日历权限。产品还没证明能把一项任务做稳，就同时铺开硬件、软件和自研模型，只会多背一条供应链和几条研发线。

更值得追求的是一个小得多的结果：一批真实用户，把一件反复发生的杂务交给了这个产品；产品能稳定做完；按无补贴的价格收费，他们仍然续费。

验证它，可以先挑一项高频任务，记下三组数：没有补贴时每次完成的真实成本、需要用户接管的比例、按正常价格收费后的留存。瓶颈在模型、在上下文检索，还是需求本身不成立，这三组数会给出答案。

补贴能给团队换来试错时间。这段时间最该做的，是找到第一件不靠补贴也能跑通的事。
