重新设计 Claude Code 的 `/config` 菜单，同一个模型 Opus 5.5 在低投入（Low）下约一分钟就做出了一版可操作的原型，调到最高投入（Max）则用了约二十八分钟。

二十八分钟版更像 Claude Code 原有的界面，还补齐了多种操作流程演示，两版都用了子菜单，也都改了搜索。但在 2026 年 9 月 25 日的[使用记录](https://claude.dev/blog/spending-your-effort/)里，作者 Thariq Shihipar 反而更愿意从一分钟版开始。

两张草图摆在一起，就能看出原因。Low 版把常规、显示、输入这类具体功能横排在顶部做标签，常规页里模型后面紧跟着主题，模型说明只写了“用于后续对话轮次”。

Max 版改成了配置页，首屏先列模型、投入和快速模式，下面再分出行为和界面两个分组。模型说明里补上了 `/model` 切换提示，还多出一项“与默认值不同的设置”（Changed from default），把改过默认值的配置单独收拢起来。

这些差异全是需要人拍板的产品取舍。主题外观要不要留在首屏，分类该按“显示、输入”切分还是按“行为、界面”归组，“与默认值不同的设置”值不值得占一个入口，都没法让模型代替产品做决定。

面对一个还在探索方向的界面改版，调到 Max 跑二十八分钟，模型会自行定下这些分组和入口，再顺着自己的方案补出多种操作流程演示。先看一分钟版，不用等这些交互演示全部展开，对照草图就能当场调整主题位置或分类命名，把下一轮修改的方向定下来。

![先在菜单草图上调整首屏顺序，再决定补哪些交互](/posts/images/ai-thinking-effort/ai-thinking-effort-01.png)

## effort 提高后，多出来的时间花在验证上

这里调节的参数叫 `effort`。按照[参数文档](https://platform.claude.com/docs/en/build-with-claude/effort)的说明，它同时影响思考、回答和工具调用的计算投入。提高 `effort` 只是让模型多花计算资源，多出来的步骤具体做什么，还得看任务本身。

在需要人工定方向的界面设计里，多花的时间容易变成未经确认的自主修改。换到对错标准明确的代码任务上，多出来的步骤就会落到源码核对和测试上。

同一篇记录里，Terminal-Bench 3.0 的 HTML/JS 安全过滤器任务（`html-js-filter`）就是例子。它改用 Fable 5.1 做组内对照，不和前面的菜单任务混比耗时，目标是过滤危险脚本并尽量保留表格、标题和无危险属性。

低投入的一次典型运行约两分钟，模型写完一个 HTML 验证页面就停了；较高投入的那次跑了约三十三分钟，模型接着去读解析器源码、检查正常页面、跑 XSS 测试集，还写了一套随机文档测试程序。

另一个根据崩溃报告修复存储引擎的任务（`mvcc-lsm-compaction`），要求在不破坏压缩功能的前提下修好故障，投入高低的差别同样落在验证顺序上。

低投入记录在构建、运行复现程序之前就改了代码，也没确认新增测试能不能抓到旧错误；较高投入记录先复现崩溃，拿不做压缩的实现当参照写出随机测试，再反过来检查测试能不能拦住不完整的修复。

过滤脚本时怕误伤表格和正常文本，修存储崩溃时怕引入压缩退化，单靠一两个正常用例很难兜住边界。多出来的步骤花在读源码、建参照和跑随机测试上，压低的是漏测回归的风险。

## 先用低档定方向，再分段提档

调高投入仍然有前提。如果原有测试集已经够用，硬让模型多跑一轮测试只会增加耗时；如果模型一开始就选错了技术方案，把投入调到最高同样解决不了问题。

一分钟和二十八分钟也只是这一次菜单任务的总耗时记录，没有拆开统计模型生成、工具执行和外部等待各占多少；其他 AI 产品的“深度思考”，也未必使用同一套 `effort` 机制。

Claude Code 支持在对话中随时用 `/effort` 调整投入，不必一个档位跑到底。**需要人做取舍的探索阶段，把决定权留在低投入的初稿里；对错能客观校验的实现和排错阶段，再把时间留给高投入的源码核对与随机测试。**

下次在 Claude Code 里开新任务，直接把首轮要求写成“先给一版可操作草图，我看完首屏结构再补交互”，确认后再用 `/effort` 分段提档，比一开始就等近半小时更省返工。
