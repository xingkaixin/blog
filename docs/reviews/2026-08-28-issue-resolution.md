## 对原建议的修正

- **PW-1**：不能只去掉 Observer 依赖。目录刷新会取消其他月份请求，仍需在新 period 到来时重新观察；已用多月份集成测试覆盖。
- **UI-6**：现有 `tagSlug()` 保留普通标签中的空格，直接使用它不能修复 ID 问题，因此选择百分号编码。
- **UI-8**：只发送 `OPEN_SEARCH_EVENT` 不能创建首次打开所需的 React root，因此快捷键仍调用真实加载入口。
- **BD-3**：已有共享产物协调器足够使用，只补齐实际缺失的渲染输入；没有再增加一个通用配置框架。
- **BD-4**：不能将 `mailto:` 一概认定为 Schema.org 违规，官方 JSON-LD 示例也使用该形式。本次属于邮箱表示规范化；更新时间部分则删除没有来源的数据。[Schema.org email](https://schema.org/email)、[dateModified](https://schema.org/dateModified)。
- **sitemap**：没有可靠修改时间时省略 `lastmod`，没有新增未经维护的更新时间字段。Google 要求这个值反映实际的重要更新。[Google sitemap 文档](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)。

## 上线与运维注意

1. 照片控制文档下次写入升级为 v4。停止旧版本发布、删除和回收进程，再使用新版工具；旧版本写入器不应继续运行。
2. `photos:gc -- --confirm --scan` 是显式操作，不会由普通 GC 自动执行。只登记超过两小时的未引用产物，随后仍等待完整 25 小时宽限期。
3. 扫描前确认没有遗留的暂停发布进程；扫描后重新执行发布命令，不恢复旧进程。年龄阈值不是无限期暂停进程的租约。
4. 公开投影不一致时，先显式运行迁移修复。首次失败上传尚无公开索引时，扫描只创建后台控制记录，迁移后才能开始回收计时。
5. v1、v2 控制文档回收记录重新等待宽限期；v3 记录保留已有回收时间和领取状态。旧媒体路径保持读取兼容，不搬迁照片。
6. frontmatter 的 YAML/TOML 日期必须写成字符串，例如 `date: "2026-08-28"`；现在会在生成器入口及时拒绝未加引号的日期。
